# 批次准入与预留：初审意见对应的实质修改

2026-10-21。0.1.0 的最小余量、差分与滞回不足以承担多作业调度职责；本轮新增同一项目下的 `admission` 包，不将旧能力重新命名为新核心。

## 要解决的决策

输入是显式父子关系的可见 cgroup 层级（允许多个调用方确认独立的根）、各节点有限的 CPU/内存准入预算和压力门禁、至多 16 个候选作业。一个作业可以同时申请多个子组的资源，作为整组启动单元；调用方提供正整数价值。输出是在所有祖先 CPU/内存约束下，总价值最大的一批作业，并给出其他作业被哪些节点/资源阻挡。

这是有界的多维 0/1 选择问题。每个作业的多个申请先沿父链汇总，兄弟子组不能分别花掉同一份祖先余量。分支定界搜索整组选择，按总价值、作业数、作业 ID 字典序确定唯一解；候选窗口上限 16，不宣称大规模在线调度或原创优化算法。

## 从建议到一次可提交的调度决策

`Ledger.plan` 只读生成私有快照，`Plan.commit` 校验账本修订号后一次性预留整批资源。提交、释放及预算刷新都推进修订号；过期方案拒绝且不修改状态。公开数组为副本，调用方修改输入或展示结果不能改变待提交内容。`release` 只释放实际存在的作业；重复释放失败。预算缩减保留已有预留并报告欠额，不撤销正在执行的作业，也不凭总体用量变化猜测作业已完成。

内存采样不是原子事务：由 `Layer` 构造节点时，有限 memory.max 减去该节点自己的 current，再与调用方的预算上限取小。CPU 只按 quota 上界与调用方策略预算取小；不把短期空闲当成可保证的 CPU。未释放作业继续全额占用账本，刷新 current 后可能保守重复扣减，明确牺牲利用率而不自动冲销。内核仍可能有外部竞争或请求估计误差。

## 必须区分结果的案例

1. 两个叶子各有 100 单位预算，各申请 60。共同父组只有 100 时只能准入一项；改为两个各有 100 的独立父组，两项都能准入。叶子指标及阈值完全不变。
2. 单节点 CPU/内存各 10。作业 A=(10,10)、价值 9，B=(6,4)、C=(4,6)、价值各 6。按单个价值或 FIFO 先拿 A 只能得 9；联合选择 B+C 得 12。保持作业不变、将 C 内存改为 7 后，最优结果变为 A。
3. 双子组协同作业需要同时获取两个分支的预算。一支压力门禁关闭时整组等待，另一开放分支的独立小作业仍可运行，不产生半组预留。
4. 两次调度从同一版本各看到足够容量。第一份方案提交后，第二份必须因版本过期失败；释放第一批后重新规划才能准入。降低预算时保留已用额度并阻止继续超分配。

以上案例均要求可执行测试、JSON 演示和独立穷举 oracle，不靠文档文字证明算法正确。该账本是单协调器进程内的逻辑预留，不是跨进程锁或内核资源保证；不负责 spawn/kill、分布式共识、抢占或通用工作流执行。
